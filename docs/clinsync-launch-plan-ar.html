وخطة إنهاء التطبيق ورفعه على Google Play و App Store خلال أسبوعين

تاريخ الإصدار: 11 سبتمبر 2026  |  الحالة الحالية: واجهة الموبايل/الويب شبه مكتملة على Mock API  |  المنصة: Expo SDK 57

هذا الملف مرجع واحد للفريق: ما الموجود اليوم في التطبيق (ويب + موبايل)، تفاصيل كل دور وشاشة، وما هي الخطوة التالية فوراً، ثم خطة عمل يومية لـ 14 يوماً حتى رفع النسخ على المتاجر.

الخلاصة بصراحة: التطبيق كواجهة (UI) متقدم جداً، لكن البيانات حالياً وهمية (Mock). خلال أسبوعين يمكن تجهيز البناء، الحسابات، سياسة الخصوصية، TestFlight، والاختبار المغلق على Google Play. النشر العام للجمهور على Google Play لحساب شخصي جديد غير مضمون في 14 يوماً لأن جوجل تطلب 12 مختبراً لمدة 14 يوماً متتالية قبل طلب صلاحية الإنتاج. App Store يعتمد على موافقة مراجعة آبل (عادة 1–7 أيام بعد الرفع).

1) الخطوة التالية فوراً (اعملوها اليوم — يوم 1)

  1. قرروا مصدر البيانات: هل يوجد Backend حقيقي جاهز؟ إذا نعم: اربطوا التطبيق عليه وأوقفوا الـ Mock. إذا لا: الإطلاق العام غير مناسب، والهدف يصبح نسخة تجريبية داخلية.
  2. افتحوا الحسابات القانونية للمتاجر اليوم: Apple Developer (99 دولار/سنة) + Google Play Console (25 دولار مرة واحدة) + حساب Expo على eas.build.
  3. انشروا سياسة خصوصية وشروط استخدام على رابط عام (صفحة ويب حقيقية، ليست localhost). المتجران يرفضان بدونها.
  4. وحّدوا اسم المنتج: الواجهة تعمل باسم Clinsync، والمستندات القديمة باسم Clinify، وPackage أندرويد com.clinify.app. اختاروا اسماً واحداً قبل الرفع.
  5. أضيفوا iOS Bundle Identifier في app.json — حالياً غير موجود، وهذا يمنع بناء iOS للستور.

بدون النقاط الخمس أعلاه، البناء للمتاجر سيكون ناقصاً أو سيُرفض.

2) ما هو المنتج؟

Clinsync نظام إدارة عيادات متعدد المستأجرين (Multi-tenant SaaS) يربط أربعة أدوار في تطبيق واحد: مريض، طبيب، سكرتارية استقبال، ومدير عيادة.

هذا ليس موقعاً منفصلاً. هو تطبيق موبايل مبني بـ React Native + Expo، ويعمل أيضاً على المتصفح كواجهة ويب من نفس الكود. ما رأيتموه على http://localhost:8081 هو نفس التطبيق، وليس ويبسايت تسويقي مستقل.

3) كيف يعمل «الويبسايت» حالياً؟

  • تطوير محلي: npm start ثم فتح المتصفح على المنفذ 8081. هذا للتجربة فقط على جهازكم.
  • الموبايل: Expo Go أو Android Emulator / جهاز حقيقي. هذا هو المنتج الأساسي للمتاجر.
  • الويب العام: غير منشور على دومين. لو أردتم نسخة ويب للعيادات لاحقاً تحتاج استضافة (EAS Hosting أو أي استضافة static) + HTTPS + نفس الـ Backend.
للمتاجر (Google Play / App Store) المطلوب هو تطبيق أصلي: ملف AAB لأندرويد وملف IPA لآيفون. نسخة الويب لا تُرفع على المتاجر.

6) الأدوار الأربعة — ماذا يرى كل مستخدم؟

أ) المريض (Patient)

التبويبات: الرئيسية · البحث · المواعيد · السجلات · الملف الشخصي

  • لوحة منزلية: مواعيد قادمة، إحصائيات، معاينة إشعارات
  • بحث عيادات وأطباء (Clinics | Doctors) مع فلتر التخصص
  • ملف العيادة: بيانات التواصل + أطباء العيادة
  • ملف الطبيب + حجز موعد (اختيار فترة + سبب الزيارة)
  • إلغاء موعد أو إعادة جدولته
  • السجل الطبي: الكل / وصفات / تحاليل / زيارات مع شاشات تفاصيل
  • تعديل الملف، الصورة الشخصية، تغيير كلمة المرور، تفضيلات الإشعارات

ب) الطبيب (Doctor)

التبويبات: لوحة التحكم · المواعيد · المرضى · الملف الشخصي

  • لوحة اليوم: عدد المواعيد، قيد الانتظار، قائمة اليوم، الإشعارات
  • تأكيد / إلغاء موعد، بدء زيارة
  • قائمة مرضى مع بحث
  • ملف المريض: بيانات، حساسية، تاريخ طبي قابل للفتح
  • شاشة الزيارة: شكوى، تشخيص، علامات حيوية، وصفات، طلبات تحاليل، إكمال الزيارة
  • جدول التوفر الأسبوعي (Schedule / Availability)

ج) السكرتارية (Secretary) — مضاف حديثاً وغير موثّق بالكامل في README

التبويبات: المواعيد · المرضى · الملف الشخصي

  • إدارة مواعيد العيادة من الاستقبال
  • تسجيل مريض جديد ثم الحجز مباشرة
  • اختيار الطبيب وتأكيد الحجز بسبب «حجز من الاستقبال»
  • الإشعارات، تعديل الملف، تغيير كلمة المرور

د) مدير العيادة (Admin)

التبويبات: لوحة التحكم · المواعيد · الأطباء · المرضى · المزيد

  • KPIs للعيادة النشطة + معاينة مواعيد وتقارير
  • إنشاء / تعديل / إلغاء تفعيل / إعادة تفعيل طبيب أو مريض
  • عرض غير النشطين (Show inactive)
  • تأكيد وإلغاء المواعيد + فلاتر الحالة
  • التقارير مع شاشة تفاصيل (metrics / highlights)
  • عرض السجلات السريرية للقراءة فقط
  • تبديل العيادة (Multi-clinic) للمستخدمين متعددي العيادات

13) خطة الـ 14 يوماً

الأيام 1–2: الأساس القانوني والإعداد

  1. تأكيد اسم التطبيق النهائي (Clinsync vs Clinify) والدومين.
  2. شراء/تأكيد حساب Apple Developer و Google Play Console.
  3. كتابة ونشر سياسة الخصوصية وشروط الاستخدام على HTTPS.
  4. إضافة في التطبيق: رابط الخصوصية في الإعدادات + شاشة موافقة عند أول تشغيل إن لزم.
  5. ضبط ios.bundleIdentifier وios.buildNumber وandroid.versionCode.
  6. إنشاء مفاتيح الإنتاج على EAS: eas credentials.
  7. وضع متغيرات الإنتاج على EAS: عنوان الـ API الحقيقي و EXPO_PUBLIC_USE_MOCK_API=false.

الأيام 3–6: إنهاء المنتج تقنياً

  1. ربط كل الـ endpoints بالسيرفر الحقيقي وإصلاح أي اختلاف في العقود.
  2. اختبار الأدوار الأربعة على جهاز حقيقي: دخول، حجز، زيارة، سكرتارية، أدمن.
  3. إخفاء حسابات الديمو من شاشة الدخول.
  4. ضبط Push للإنتاج (Firebase لأندرويد + APNs لآبل).
  5. مراجعة الأذونات: الصور فقط حالياً — لا تطلبوا صلاحيات زائدة.
  6. تشغيل npm run typecheck وسيناريوهات Maestro الأساسية.
  7. لقطات شاشة عربية (وهاتف آيفون 6.7" و 6.5" وأندرويد فون).

الأيام 7–9: البناء

  1. بناء أندرويد إنتاج: eas build --platform android --profile production → ملف AAB.
  2. بناء iOS إنتاج: eas build --platform ios --profile production → ملف IPA (يمكن من ويندوز عبر EAS Cloud، لا تحتاج ماك للبناء).
  3. تثبيت نسخة داخلية على أجهزة الفريق والتأكد أن الـ Mock مغلق.
  4. إصلاح أي كراش فوراً وإعادة البناء.

الأيام 10–12: الرفع على المتاجر (اختبار أولاً)

  1. Google Play: إنشاء التطبيق، استكمال التصنيف، Data Safety، سياسة الخصوصية، ثم رفع AAB على Internal ثم Closed testing.
  2. دعوة 12 مختبراً على الأقل إن كان الحساب شخصياً جديداً — وابدأوا العدّاد من اليوم لأن الإنتاج العام ينتظر 14 يوماً.
  3. App Store Connect: إنشاء التطبيق، الفئة Medical أو Productivity، Privacy Nutrition Labels، رفع IPA عبر eas submit --platform ios.
  4. توزيع TestFlight على الفريق.

الأيام 13–14: المراجعة والإرسال

  1. إصلاح ملاحظات المختبرين.
  2. إرسال نسخة App Store للمراجعة (Submit for Review) إذا اكتملت الميتاداتا.
  3. على Play: الإبقاء على Closed testing إن لم تكتمل نافذة الـ 14 يوماً، أو التقديم للإنتاج إن كان الحساب مؤسسة/قديماً ويستوفي الشروط.
  4. تجهيز رد المراجعة: حساب تجريبي حقيقي للمراجع (طبيب + مريض) على السيرفر، وليس Mock.

14) Google Play — الخطوات العملية

  1. ادفعوا 25 دولار مرة واحدة على play.google.com/console.
  2. Create app: الاسم Clinsync، لغة عربية، تطبيق مجاني أو مدفوع حسب النموذج التجاري.
  3. أكملوا: محتوى التطبيق، الفئة (طب)، الفئة العمرية، سياسة الخصوصية، Data safety (بيانات صحية + حسابات + جهاز).
  4. أول رفع AAB غالباً يذهب Internal testing. بعد نجاحه انقلوا إلى Closed testing.
  5. أوامر مقترحة: 
    npx eas-cli login
npx eas-cli build --platform android --profile production
npx eas-cli submit --platform android --latest
  6. جوجل لا تنشر للجمهور تلقائياً بعد الرفع. أنتم تروّجون المسار (Promote) بعد اكتمال المتطلبات.

الحسابات الشخصية الجديدة بعد 13 نوفمبر 2023: Closed test بـ 12 مختبراً لمدة 14 يوماً متصلة ثم Apply for production.

15) Apple App Store — الخطوات العملية

  1. Apple Developer Program: 99 دولار/سنة. انتظروا تفعيل الحساب (قد يأخذ ساعات حتى يومين).
  2. في app.json أضيفوا مثلاً: 
    "ios": {
  "bundleIdentifier": "com.clinify.app",
  "supportsTablet": true,
  "infoPlist": {
    "ITSAppUsesNonExemptEncryption": false
  }
}
    اضبطوا قيمة التشفير حسب الواقع إن استخدمتم تشفيراً غير المعفى.
  3. أنشئوا التطبيق في App Store Connect بنفس Bundle ID.
  4. ارفعوا IPA: 
    npx eas-cli build --platform ios --profile production
npx eas-cli submit --platform ios --latest
  5. بعد المعالجة يظهر البناء في TestFlight خلال نحو 10–15 دقيقة (أحياناً أطول).
  6. أكملوا: الاسم، الوصف العربي، الكلمات المفتاحية، لقطات الشاشة لكل مقاس مطلوب، رابط الخصوصية، بيانات الاتصال، تصنيف العمر.
  7. Submit for Review. راجعوا إرشادات آبل للخصوصية والبيانات الصحية: لا إعلانات على البيانات الطبية، ووضوح الغرض.

EAS Submit يعمل من ويندوز؛ لا حاجة لماك للرفع. الماك مفيد للاختبار على Simulator فقط.

16) صفحة المتجر — نصوص مقترحة (عربي)

الاسم: Clinsync — إدارة العيادات

وصف قصير (Play، حتى 80 حرفاً): احجز موعدك وتابع سجلك الطبي — للطبيب والمريض والعيادة.

وصف كامل (مختصر للستور):

  • للمرضى: البحث عن عيادة/طبيب، حجز، إلغاء، سجل وصفات وتحاليل وزيارات.
  • للأطباء: جدول اليوم، بدء الزيارة، الوصفات وطلبات التحاليل، جدول التوفر.
  • للاستقبال: تسجيل مريض وحجز فوري.
  • للإدارة: مؤشرات، تقارير، إدارة الأطباء والمرضى.
  • عربي بالكامل مع وضع ليلي.

لا تكتبوا «يعالج» أو «يشخّص» كادعاء طبي. التطبيق أداة إدارة مواعيد وسجلات، وليس جهاز طبي.

18) أوامر التشغيل والبناء

npm run web
npm run android
npm run typecheck

# إنتاج أندرويد (AAB للمتجر) — بعد ضبط production env
npx eas-cli build --platform android --profile production

# APK للتجربة الداخلية فقط
npm run build:apk

# إنتاج iOS
npx eas-cli build --platform ios --profile production

# رفع
npx eas-cli submit --platform android --latest
npx eas-cli submit --platform ios --latest

بروفايل preview الحالي يخرج APK ويفعّل Mock — لا تستخدموا هذا البروفايل للمتاجر.

19) مخاطر مهمة لتطبيق عيادات

  • بيانات صحية: يلزم الإفصاح في المتجرين، وتشفير النقل (HTTPS)، وعدم تسريب بيانات في السجلات.
  • مصر / المنطقة: راجعوا متطلبات حماية البيانات المحلية مع المستشار القانوني إن وُجد.
  • مراجع آبل: أعطوهم حساباً يعمل على السيرفر الحقيقي. التطبيق الذي لا يعمل للمراجع يُرفض.
  • لا ترفعوا نسخة Mock على أنها منتج طبي حقيقي.
  • اختلاف الأسماء (Clinsync / Clinify / doctors-app) يربك الشهادات والستور — وحّدوا قبل البناء النهائي لأن Bundle ID و Package لا يتغيران بسهولة بعد أول رفع.

20) قائمة تسليم نهاية الأسبوعين

  1. التطبيق مربوط بسيرفر حقيقي (أو قرار رسمي أن الإطلاق داخلي فقط).
  2. سياسة خصوصية منشورة + رابطها داخل التطبيق وفي المتجرين.
  3. AAB مرفوع على Play (Internal/Closed).
  4. IPA ظاهر في TestFlight، وإن اكتملت الصفحة: Submit for Review.
  5. حسابات تجريبية للمراجعين.
  6. لقطات شاشة ووصف المتجر بالعربي.
  7. 12 مختبراً بدأوا Closed testing إن لزم لحساب Play الشخصي.
  8. Sentry أو مراقبة بديلة مفعّلة اختياريًا.
ابدأوا غداً صباحاً بهذا الترتيب فقط: 1) قرار الـ Backend   2) فتح حسابات المتاجر   3) سياسة الخصوصية على دومين   4) Bundle ID لآيفون وتوحيد الاسم   5) ضبط production على EAS وإيقاف الـ Mock.
